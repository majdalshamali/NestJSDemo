# 0001. Adopt Better Auth for authentication

**Date**: 2026-09-19
**Status**: In Progress

## Summary

This decision adds sign up, sign in, and session handling to the API using Better Auth (an open source authentication library), replacing the current hand made Users module. People sign up and sign in with email and password, get back a bearer token (a credential sent in a request header) for later requests, and get one of two roles: regular user or admin. The NestJS glue code (how routes are guarded, how the session is read) is written by hand rather than through a ready made wrapper package, because that wrapper does not yet support the NestJS version this project runs.

## Requirements

**User stories**:
- As a visitor, I want to create an account with my email and password so that I can use the API as a known user.
- As a returning user, I want to sign in and receive a credential so that I can make authenticated requests.
- As an authenticated user, I want to view my own user record, but not other people's, unless I am an admin.
- As an admin, I want to list and view every user, and promote users, so that the app can be operated day to day.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
- **AC-1**: A visitor can sign up with email, password, and name via `POST /api/auth/sign-up/email` and receives a session (a bearer token) in the response.
- **AC-2**: A registered user can sign in with the correct email and password via `POST /api/auth/sign-in/email` and receives a bearer token; a wrong password or unknown email both return the same generic 401, never revealing which one was wrong.
- **AC-3**: `GET /users/:id` succeeds when the caller's own user id matches `:id`, or the caller has the admin role; a caller who is neither the owner nor an admin receives 403.
- **AC-4**: Any route carrying the custom auth guard rejects a request with no valid bearer token with 401.
- **AC-5**: `GET /users` (list all users) succeeds only for a caller with the admin role; any other authenticated caller receives 403.
- **AC-6**: Every `/api/auth/*` route enforces Better Auth's built in rate limits (its defaults, tighter on sign in and sign up), with counters stored in the database so they survive a server restart.
- **AC-7**: A user whose `banned` field is set cannot sign in, and an existing session for that user stops working.
- **AC-8**: `POST /users` no longer exists; creating a user only happens through sign up.
- **AC-9**: A one time seed script can set an existing user's role to admin, so the first admin can be created without any self service promotion path in the running app.

## Decision

**Chosen option**: Option 1: Better Auth, hand rolled NestJS integration

Adopt `better-auth` as the authentication engine, using its Prisma adapter, `admin` plugin (roles), and `bearer` plugin (token based sessions), wired into NestJS by hand rather than through `nestjs-better-auth`.

## Feature design

**Data model sketch**:

| Entity | Key fields | Notes |
|---|---|---|
| **User** (PK `id`, string) | `email` (unique), `emailVerified` (bool), `name`, `image?`, `role` (`user` \| `admin`, default `user`), `banned?`, `banReason?`, `banExpires?`, `createdAt`, `updatedAt` | Replaces the current `User` model; the id type changes from integer to string |
| **Session** (PK `id`) | `userId` (FK to User), `token` (unique), `expiresAt`, `ipAddress?`, `userAgent?`, `createdAt`, `updatedAt` | One User to many Session |
| **Account** (PK `id`) | `userId` (FK to User), `providerId`, `accountId`, `password?` (hashed) | One User to many Account; only one row per user in this build (email and password only) |
| **Verification** (PK `id`) | `identifier`, `value`, `expiresAt` | Generated by Better Auth by default; unused in this build since email verification and password reset are out of scope |

`Session` and `Account` rows are removed when their `User` is removed (cascade delete, Better Auth's default adapter behaviour).

**State transitions**:

Session: created at sign in → active → ends by explicit sign out (deleted) or by reaching `expiresAt` (default 7 days, treated as expired on next use).
User.role: starts at `user` on sign up; moves to `admin` only through the seed script (this build) or a later admin hosted promotion route (not built yet, see Follow up).

**API surface**:

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| /api/auth/sign-up/email | POST | email, password, name | user, bearer token | public | 422 invalid email or password |
| /api/auth/sign-in/email | POST | email, password | user, bearer token | public | 401 invalid credentials (generic, same for wrong password or unknown email) |
| /api/auth/sign-out | POST | bearer token (header) | success flag | bearer | 401 no active session |
| /api/auth/get-session | GET | bearer token (header) | session, user | bearer | 401 no or expired session |
| /api/auth/admin/set-role | POST | userId, role | updated user | bearer, admin role | 403 caller is not admin |
| /users | GET | bearer token (header) | array of users | bearer, admin role | 403 caller is not admin |
| /users/:id | GET | id (path), bearer token (header) | user | bearer, self or admin role | 401 no session, 403 not self or admin, 404 not found |

The `/api/auth/*` routes are generated by Better Auth and its plugins, not hand built; the table above lists the ones this feature relies on. `POST /users` is removed (AC-8).

**Value sourcing** (every value each action produces, computes, or displays names where it comes from):

| Action | Value produced / displayed | Source |
|---|---|---|
| GET /users/:id | whether the caller may view this record | compare `session.user.id` (from the bearer token, via `auth.api.getSession`) to the `:id` path param; allowed if equal, or if `session.user.role === "admin"` |
| GET /users | whether the caller may list all users | `session.user.role` from the resolved session; allowed only when `"admin"` |
| sign up / sign in | the hashed password | computed internally by Better Auth (`scrypt`, its default); never handled or stored by app code |
| any /api/auth/* request | the rate limit counter for that route and IP | Better Auth's own database backed rate limit store (a table it creates), not app code |
| first admin | which user becomes admin | not derived from any request; set explicitly by the person running the seed script (AC-9), by user id or email they choose |
| any authenticated request | whether a banned user's session is rejected | Better Auth's `admin` plugin deletes all of a user's existing sessions the moment they are banned (confirmed during the build); the hand rolled `AuthGuard` also checks `session.user.banned` itself as a second line of defence, in case a ban is ever applied a different way (e.g. a direct database write) |

**Key invariants**:
- `User.email` is unique.
- Every `Session` and `Account` row references an existing `User` (foreign key, cascade delete).
- `User.role` is `user` or `admin`; new sign ups always start at `user`.
- Exactly one `Account` row per user in this build (only the email and password provider is enabled).

**Security model**:
- Public (no session required): `POST /api/auth/sign-up/email`, `POST /api/auth/sign-in/email`, and the existing `/api/*` Arcjet demo routes and `GET /` (unaffected by this feature).
- Requires a valid session (any role): `POST /api/auth/sign-out`, `GET /api/auth/get-session`, `GET /users/:id` when requesting one's own id.
- Requires a valid session with the admin role: `GET /users`, `GET /users/:id` for any id other than the caller's own, and Better Auth's admin plugin routes (`set-role` and similar).
- No regulated data (payments, health) is in scope; the only personal data is account email and name, already comparable to what the current Users module stores.

**Configuration required**:
- `BETTER_AUTH_SECRET`: signing and encryption secret for sessions and tokens, 32 or more characters (`openssl rand -base64 32`).
- `BETTER_AUTH_URL`: this API's own base URL (e.g. `http://localhost:3000`); also becomes the automatically trusted origin.

**Critical test scenarios**:
- Happy path: sign up, sign in, call `GET /users/:id` for one's own id and receive the record, verifies **AC-1**, **AC-2**, **AC-3**.
- Failure case: sign in with a wrong password and with an unregistered email both return the same 401 shape, verifies **AC-2**.
- Auth/permission: an authenticated, non admin caller requesting `GET /users` receives 403; the same caller requesting another user's `GET /users/:id` receives 403; a caller with no bearer token receives 401, verifies **AC-3**, **AC-4**, **AC-5**.

## Build plan

1. [x] Add `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` to `.env` and `.env.example`. Satisfies **AC-1**, **AC-2**.
2. [x] Create the Better Auth server config (e.g. `src/auth/auth.ts`): Prisma adapter, `emailAndPassword.enabled: true`, `plugins: [admin(), bearer()]`, `rateLimit: { storage: "database" }`, secret and base URL read from env. Written before the schema is generated, because Better Auth's generator introspects this config to know which plugin fields to emit. Satisfies **AC-1**, **AC-2**, **AC-5**, **AC-6**, **AC-7**.
3. [x] Remove the current `User` model from `prisma/schema.prisma`, generate Better Auth's schema from the config in step 2 (`npx auth@latest generate --output prisma/schema.prisma`), and run `prisma migrate dev` for the new migration. Because the `admin` plugin is already registered in step 2's config, the generated schema includes `role`, `banned`, `banReason`, `banExpires` on `User`. This replaces the integer id `User` table; any existing local rows are lost. Satisfies **AC-1**, **AC-2**, **AC-3**, **AC-5**, **AC-7**, **AC-8**.
   (Built as: generate ran clean; `migrate dev` cannot run non-interactively, so the migration SQL was produced with `prisma migrate diff` and applied with `prisma migrate deploy`, same net result. The one pre-existing `User` row was dropped, as warned above.)
4. [x] Update `main.ts`: create the app with `bodyParser: false`, mount Better Auth's handler (`toNodeHandler(auth)`) on `/api/auth/*`, then explicitly re-enable body parsing for every other route with `app.use(express.json())` (`bodyParser: false` turns off parsing for all routes, not just the auth ones; without this, any POST/PATCH/PUT outside `/api/auth/*`, including the existing Arcjet demo routes, would silently see an empty body). Satisfies **AC-1**, **AC-2**, **AC-6**.
   (Built as: `expressApp.all('/api/auth/*splat', toNodeHandler(auth))`, not `app.use(prefix, ...)` — Express 5's `app.use` strips the mount prefix from `req.url`, which breaks Better Auth's own route matching.)
5. [x] Write a custom guard (`AuthGuard`) that resolves the session via `auth.api.getSession` from the request headers and attaches it to the request, throwing 401 when absent; an admin check (guard or shared helper) for admin only routes; and a `@Session()` param decorator to read the attached session in controllers, mirroring the existing `ArcjetGuard` pattern. Satisfies **AC-3**, **AC-4**, **AC-5**.
6. [x] Rewrite `UsersController` and `UsersService` against Better Auth's `User` model: remove `POST /users`; apply the new guard plus an admin check to `GET /users`; apply the new guard plus a self or admin check to `GET /users/:id`. Satisfies **AC-3**, **AC-5**, **AC-8**.
7. [x] Write a one time admin bootstrap script (e.g. `npm run seed:admin -- <email>`) that sets `role = "admin"` for the given user via Prisma. Satisfies **AC-9**.
8. [x] Update the README (stack table, API section, env var table, design notes) to document sign up, sign in, the new `/users` behaviour, and the admin bootstrap step. Supports **AC-1** through **AC-9**.

## Consequences

**Positive**:
- Requests to user data now require identity and are scoped by ownership or role, closing the current fully open `/users` surface.
- Session, token, and password handling rest on a maintained library instead of ad hoc code.
- No new runtime infrastructure: reuses the existing Postgres database through the same Prisma connection.

**Negative / tradeoffs**:
- The hand rolled guard, admin check, and decorator are this project's own code to maintain, rather than an imported one; a `nestjs-better-auth` upgrade to NestJS 12 support later would be a candidate to revisit this decision.
- The existing `User` table's integer id becomes a string id; any local rows in the current table are lost when the migration runs.
- Password reset and email verification are not built in this pass; an account holder who forgets their password has no self service recovery yet.

**Neutral**:
- The `Verification` table exists in the schema from day one (Better Auth's default) even though nothing in this build writes to it yet.
- The admin plugin's `banned`, `banReason`, `banExpires` fields exist on `User` from day one even though no route to set them is built yet.
